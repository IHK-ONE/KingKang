KingKang 移动终端

一款内置终端、可在 Android 设备本地运行 Linux、并以 Kali 为最终目标的应用。无 root 用户通过标准模式和内置 Kali 终端体验 Kali，并在设置中安装 DeepSeek Harness（dsh）作为 Agent 核心；root 玩家保留 chroot、完整终端与高级扩展。本文给出技术路线、可二开的开源基座、系统架构、Kali 集成、终端体验、发行合规与实施计划。

Target OS
Android 10–17
Primary ABI
arm64-v8a
Default runtime
PRoot，无 root
Product
标准 / Pro / 远程三模式
结论先行
  1. 产品形态：一个 GPLv3 应用、三条运行时。标准模式（无 root，PRoot）面向普通用户；Pro 模式（root，chroot）面向进阶玩家；远程模式（SSH）作为补充。不要拆成两个 App。
  2. 代码基座：fork termux-app 的终端、PTY 与会话核心，重写 app 层为 Kali 优先的 Compose 工作台。不要直接把 Termux 的开发者 UI 当作最终产品。
  3. 无 root 体验：用标准模式（PRoot）与内置 Kali 终端承载功能体验；Agent 核心采用安装在 Kali 内的 DeepSeek Harness（dsh）。PRoot 下不承诺监听模式、注入、HID 或 raw socket。
  4. Kali：以官方 NetHunter Rootless 的 rootfs 与启动流程为准。proot-distro 的官方发行版列表不收录 Kali，社区方案可用，但不适合作为产品基线。
  5. 发行：以 F-Droid、自建仓库和 APK 直发为主。Google Play 的 W^X 变通方案脆弱且有政策风险，不适合作为唯一渠道。
01 / Scope

目标与边界

这个产品不是“能连 SSH 的终端”，而是在 Android 应用沙箱里维护一套真实的 Linux 用户空间：有 rootfs、有包管理器、有本地进程，Kali 是最终交付形态。终端只是它的入口。

范围内

  • 一键下载、校验、解压并启动 Debian / Kali rootfs
  • 多标签终端、会话保活、前台服务与通知
  • apt / pip / git / 编译工具链等本地命令
  • 内置 Kali 终端，以及 DeepSeek Harness（dsh）核心的安装、版本检测、更新与原生对话
  • 标准 / Pro / 远程三种模式，共用同一份 rootfs
  • 可选的图形界面（VNC / X11）
  • root 设备上的 chroot 增强模式
  • SSH 到远程主机，作为第三条运行时

范围外

  • 自动 root、自动刷入内核或 recovery
  • 内置漏洞利用、凭据或武器化载荷
  • 承诺无 root 下的监听模式、数据包注入、USB HID
  • 替代桌面 Linux 或通用 Android 开发环境
  • iOS / 桌面端（架构可复用，不在本期）

产品定位是“移动端的本地 Linux 工作台”，面向安全学习者、授权测试人员、需要在手机上跑工具链的开发者，以及需要离线应急环境的运维人员。Kali 工具的使用范围必须在首次启动时明确提示：仅限授权目标与合法用途。

1.1 真正决定架构的约束

约束具体表现设计应对
Android 10+ W^XtargetSdk ≥ 29 的应用不能对应用数据目录中的文件调用 exec()。Termux 长期停在 targetSdk 28 就是为了绕开这条限制。FOSS 版保持 28；现代 targetSdk 版本需要 APK 原生库 / linker64 变通，或只做 root 模式。
SELinux untrusted_app普通应用没有 CAP_NET_RAW，不能 mount，不能改内核网络配置。PRoot 的假 root 只改路径解析，不给内核权限。把能力差异写进 UI；需要 raw socket 时提示切换 root 模式，而不是假装支持。
非特权 user namespaceAndroid 普遍不向普通应用开放，rootless 容器（runc / podman）不可用。用 PRoot 的 ptrace 路径重写作为无 root 方案；不要把它宣传成安全隔离。
Phantom process killerAndroid 12+ 会在子进程超过约 32 个或 CPU 异常时杀进程，表现为 signal 9。前台服务 + 会话保活 + 在应用内给出 ADB/开发者选项指引；不要静默改系统设置。
16 KB 页大小Android 15+ 的 16 KB 页设备要求原生库与可执行文件正确对齐，发行版二进制也需要重建或验证。NDK r28+、-Wl,-z,max-page-size=16384；把 16 KB 设备纳入发布门禁。
Google Play 政策“下载并执行代码”与安全工具类应用都容易被审查；Termux 的 Play 版本依赖额外的 exec 变通。主渠道不依赖 Play；Play 作为独立 flavor，而不是唯一构建。
无 KVM、设备碎片化应用拿不到 KVM；QEMU 只能用 TCG；OEM ROM 的后台策略差异很大。VM 只做研究项；运行时引擎抽象；建立设备兼容矩阵。
02 / Runtime

路线选择：Linux 以什么形态存在

先决定 Linux 运行在哪里，再谈终端和 UI。五条路线的能力边界差别很大，不能靠后期优化弥补。

路线需要 root性能本地 Kali主要限制结论
Termux 原生否原生否，需 PRoot 才是完整发行版不是 Kali 发行版；包集合独立仅作基座
PRoot 无 root chroot否系统调用密集场景约 1.5–5× 开销，CPU 密集接近原生是，NetHunter Rootless无 raw socket、mount、systemd；不是安全沙箱默认
Root chroot是接近原生是依赖 root 方案与设备；SELinux/挂载差异可选增强
QEMU / AVF 虚拟机否 / 部分TCG 慢一个数量级；AVF 设备受限是，运行自己的内核体积、发热、兼容性、开发量大研究项
SSH / 云主机否取决于网络与远端仅远程离线不可用；依赖账号与网络附加

2.1 为什么默认 PRoot

PRoot 通过 ptrace 拦截子进程的系统调用，把路径重写到 rootfs 内，并用 -0 伪造 uid 0。它不需要 root，也不需要内核支持 user namespace，因此在绝大多数 Android 设备上可用。代价是所有系统调用多一层用户态转发，apt、git、编译这类系统调用密集的操作会明显变慢。

必须明确：PRoot 不是安全边界。容器里的“root”只是伪造的 uid，恶意程序仍然以应用 uid 运行，能读写应用私有数据；如果绑定了共享存储，也能读写用户文件。产品的安全模型必须按“运行受信任的发行版”来设计，而不是按“运行不可信代码”来设计。

2.2 为什么保留 root chroot

检测到设备已 root 时，通过 su 进入真实 chroot，能获得接近原生的性能、真实的 mount、raw socket 和 iptables 能力。它仍然不能凭空提供 Wi-Fi 监听模式或 USB HID，那需要 NetHunter 内核与驱动。chroot 模式的工程重点是挂载生命周期和退出清理：/dev、/proc、/sys 必须成对挂载与卸载，异常退出不能留下脏挂载。

2.3 为什么暂不做 VM

Android 应用无法直接使用 KVM，QEMU 只能跑 TCG，启动和 I/O 都慢一个数量级；AVF 只在部分新设备上可用，且不是通用的 Kali 交付方案。VM 的优势是“真内核”，但 MVP 的用户价值主要来自 apt、脚本和 CLI 工具，PRoot 已能覆盖。把 VM 留到有明确付费场景时再评估。

架构决定

从第一天就把运行时抽象成 RuntimeEngine，默认实现 PRoot，root 设备追加 Chroot，远程追加 SSH。不要在 UI 或会话层散落 proot 命令拼接，否则以后接 Play 变通方案或 VM 会重写一遍。

2.4 推荐的产品形态：一个应用，三条运行时

普通用户和 Pro 玩家不应该用两个 App 解决。同一个应用、同一份 rootfs，用运行时能力分层；用户换设备或 root 后，模式可以原地升级，不需要重装或迁移数据。

模式前提运行时能做什么面向
标准模式无 rootPRootKali 终端、apt、可用的 CLI 工具、KeX 桌面、DeepSeek Harness（dsh）普通用户、学习者
Pro 模式已 rootchroot标准模式全部 + raw socket、mount、iptables、原生性能、自定义 rootfs、X11、SSH/自动化进阶玩家、专业测试
远程模式任意SSH远端 Kali 的完整能力；本地只做终端与文件传输需要完整能力但不想 root 的用户

模式不是三个 App，也不是三套安装包。标准与 Pro 共用同一份 Kali rootfs，只切换执行引擎；远程模式复用同一个终端与工具目录。UI 在启动时检测 root 与 SSH 配置，给出“可用能力”而不是弹一堆权限请求。

2.5 Agent 核心：DeepSeek Harness（dsh）

对话界面只是壳，Agent 能力由安装在 Kali rootfs 内的 DeepSeek Harness 提供。dsh 是 DeepSeek 官方以 npm 包 @deepseek-ai/dsh 分发的 agent harness CLI，支持 web、tui、headless 三种 profile。把它装在 Kali 内而不是 Android 侧，会话可以直接使用同一环境里的 nmap、sqlmap 等工具，不需要跨进程拼接命令。

设置页提供独立的“Agent 核心”卡片：未安装时只显示安装，安装后只保留检查更新（发现新版本自动更新）与卸载，用户不必回到终端手动处理 Node 与 npm：

  • 安装：应用直接用 HTTPS 从 nodejs.org/dist 下载当前架构的 Node.js 24 官方 tarball，在应用内校验 SHA-256 后流式解压到 /opt/kingkang/node，不依赖 Kali 的 apt 或 curl；随后执行 npm install -g --prefix /opt/kingkang/dsh @deepseek-ai/dsh@latest，并把入口链接到 /usr/local/bin/dsh。dsh 的依赖树较大，安装后约 1.4 GB（另占约 300 MB npm 缓存），首次安装视网络需要 20–40 分钟，界面显示当前步骤并允许取消。
  • 版本：读取 dsh --version 与 npm view @deepseek-ai/dsh version，明确显示已安装版本、Node 版本，以及“已是最新”或“可更新到 x.y.z”。
  • 更新：重新执行同一套 npm 安装并刷新链接；安装前缀固定，不覆盖系统 Node。更新失败时保留日志，可在设置中重试。
  • rename 兼容层：Android 给应用进程装的 seccomp 过滤器把旧的 rename(2) 系统调用直接回 ENOSYS，而这个过滤器会被 PRoot 启动的所有 guest 进程继承；npm 正是用 rename 把下载内容挪进缓存，于是第一次写缓存就失败（npm 把错误改写成 EEXIST，日志里能看到真实的 ENOSYS: rename）。应用在第一次启动 PRoot 会话前，用 Kali 自带的 gcc 把一小段 rename() 兼容库（改用 renameat2(2)）编译到 /usr/local/lib/kingkang/libkkrename.so，之后终端与所有脚本都以 LD_PRELOAD 加载它；镜像里没有 gcc 时跳过，会话照常启动。
  • 执行：安装与检查在 PRoot 内以一次性脚本运行，有超时、可取消；Kali 环境未就绪时禁用入口。脚本与下载日志留在 Kali 的 /tmp，不依赖来源不明的远程安装脚本。

对话链路：KK-Agent v1

对话不是 WebView，也不把 dsh 的 RPC 泄漏到 UI。应用启动一个 Node 侧车 bridge.mjs，两者通过 stdio 上的 NDJSON 通信；侧车再以 --profile web 启动 dsh，只绑定 127.0.0.1，并消费它的 SSE 事件流。应用只认识稳定的 KK-Agent v1 事件（文本增量、工具调用、审批、提问、队列、投影），dsh 改事件名或字段时由侧车吸收，不必重发 APK。

  • 会话归属：会话、历史、标题、模型选择全部由 dsh 保存，应用不维护第二份 chats.json。恢复会话时按 seq 分页读取更早历史。
  • 生命周期：前台服务持有桥接进程；停止、重启、切换会话与 dsh 语义一致。流中断会在对话内明确提示，并可从设置重启桥接。
  • 子 Agent：顶部条显示 dsh 委派出的直接子会话及运行状态；打开后复用同一套转录渲染，可继续对话或停止（仅 continuable），一次性子 Agent 保持只读。子 Agent 再向下委派时按同一路径逐层下钻（“下级子 Agent”），返回按钮一级一级退回，能走多深由 dsh 的委派深度上限决定（应用不覆盖 dsh 默认配置）；子会话不会混进会话列表。dsh 拒绝的操作会在界面上明确提示，而不是静默失败。
  • 界面：流式回答与思考过程、工具卡片、审批/提问、待办与计划、排队/引导消息、模型选择、停止与归档都是原生 Compose 组件，与终端、设置共用同一套视觉语言。
  • 安全：没有面向应用的 HTTP 监听；dsh 的 loopback 服务不暴露到局域网；模型输出只作为文本/卡片渲染，永不作为 HTML 执行。

Kali 的 kali-motd 会在登录 shell 里无条件打印 “This is a minimal installation of Kali Linux”，即使是完整的 NetHunter 镜像也一样，容易让人误以为装错了版本。应用在准备运行目录时按 Kali 自己的用户级开关写入 /root/.local/share/kali-motd/disable-minimal-warning，只隐藏这一段提示；该文件位于 /root，镜像更新时随用户数据保留。

产品判断

dsh 是“可安装、可升级的 Agent 核心”，应用提供原生对话而不是嵌网页。当前版本已接通安装、版本、更新、卸载与 KK-Agent 对话链路；图片附件、斜杠命令（来自 dsh 的命令注册表）、会话权限预设、凭据图形化配置与子 Agent 面板都已接入；dsh 原生工具卡片视图尚未接入，缺失时退回通用工具卡片，界面不伪造分析结果。安装源只使用 DeepSeek 官方 npm 包与 nodejs.org 官方二进制。

3.1 三条现实可行的二开路径

策略做法到可运行原型许可证结果适合
A · 整体 fork termux-app（M0 验证）换包名与品牌，保留终端与 PTY 层，先跑通 Kali 链路2–4 周整个应用 GPLv3最快验证；不作为最终产品形态
A+ · fork 核心 + 新壳（推荐）复用 terminal/PTY/会话服务，重写 app 层为 Kali 工作台；新增 dsh 核心与能力检测6–8 周整个应用 GPLv3产品化；同时服务普通用户与 Pro
B · 新壳 + Apache 模块Compose 新应用，抽 terminal-emulator/terminal-view，自写 PTY JNI 与运行时管理8–12 周可闭源；保留 Apache NOTICE商业产品、需要品牌与 UI 控制
C · 包一层 AnLinux 脚本调用 Termux 安装脚本，应用只做向导与按钮2 周Apache-2.0验证需求，不适合作为独立产品
D · fork UserLAnd在其 PRoot 管理上改 UI—许可证不明不建议，先解决法务问题
已定方案 · GPLv3

既然接受 GPLv3，推荐 A+：fork termux-app 的运行时核心（terminal-emulator、terminal-view、PTY/exec、会话服务），但不要把它的开发者 UI 当作最终产品。用新的 Compose 工作台重写 app 层，保留 Termux 的核心能力。M0 可以先整体 fork 验证链路，M1 起抽核心、替换界面。这样既不重造终端轮子，也不会被 Termux 的产品形态限制。

3.2 GPL 边界与许可证审计

  • GPLv3 应用代码：链接或包含进同一个应用，整个应用按 GPLv3 分发；需要提供完整对应源码、安装信息，且不能附加额外限制。闭源商业版不能走这条路。
  • Apache-2.0 终端模块：可以进入闭源应用，但要保留 LICENSE/NOTICE、标注修改，并遵守专利与商标条款。抢手的“Termux 终端”多数价值就在这两个模块。
  • PRoot 二进制：GPLv2。通常作为独立进程分发，随包提供源码或书面要约；不要把它编译成静态库链接进应用。具体是否构成衍生作品，交给法务确认。
  • GPLv2 与 GPLv3 混用：NetHunter App 的 LICENSE 是 GPLv2 文本。若项目未声明 “or later”，把它与 GPLv3 的 termux-app 代码直接合并可能不兼容；按独立模块、独立进程或仅参考处理最稳。
  • Kali 工具与 rootfs：工具许可证混合，例如 Nmap 使用 NPSL（非标准开源许可），打包进应用商店前需要逐项审计。发行 rootfs 镜像和自己分发 Kali 是两件事。
  • 商标：不要使用 Kali 的龙形 logo 或暗示官方背书；“Kali Linux”仅作描述性使用，应用名与图标必须独立。

04 / Architecture

总体架构

核心是把“终端 I/O”和“Linux 运行时”解耦。终端只负责字节流、渲染与输入；运行时负责把字节流接到 PRoot、chroot 或 SSH 上。这样更换执行引擎不会影响 UI。

4.1 层职责

层职责关键实现
UI终端标签、文件、设置、首次启动向导Kotlin + Jetpack Compose；终端表面用 Canvas 或 Termux TerminalView
Session会话生命周期、后台保活、通知、恢复前台服务；每会话一个 PTY 读线程；元数据落 DataStore
Terminal CoreVT 状态机、字符宽度、回滚、选择与搜索复用 Apache-2.0 模块，或 libvterm + 自写渲染
PTY Bridge创建伪终端、fork/exec、窗口大小、信号JNI + posix_openpt/fork；或 Termux 的 TermExec
Runtime Engine把命令翻译成 PRoot / chroot / SSH 启动参数RuntimeEngine 接口，三个实现，统一清理语义
Rootfs下载、校验、解压、版本与镜像管理OkHttp + libarchive；manifest 签名；断点续传
GUI BridgeVNC / X11 会话MVP 用外部 VNC 客户端 intent；P2 内置客户端或 Termux:X11
Android 集成存储、剪贴板、分享、通知、键盘、电量SAF、FileProvider、ForegroundService、WakeLock

4.2 进程与线程模型

  • 主进程承载 UI、前台服务与原生 PTY 桥接；不要把 proot 或 shell 跑在应用主进程里。
  • 每个会话：一个 PTY 读线程、一个有界写队列、一个渲染器。输出洪峰时丢帧不丢字节，背压传递到 PTY 读端。
  • 下载与解压各自使用独立工作线程/前台任务，支持取消与断点。解压期间不做终端渲染的重活。
  • 会话状态：CREATED → PREPARING → READY → RUNNING → STOPPING → STOPPED，异常进入 FAILED。chroot 模式在 STOPPING 必须执行卸载清理。
  • 应用被系统杀死后，PTY 不能恢复；用 tmux 或重新拉起会话作为恢复策略，不要假装能无缝恢复进程。

运行时接口

interface RuntimeEngine {
    val id: EngineId
    suspend fun prepare(ref: RootfsRef): PreparedRootfs
    fun start(spec: SessionSpec): PtyHandle
    fun stop(handle: PtyHandle, reason: StopReason)
}

PTY 创建（JNI / C，简化）

int master = posix_openpt(O_RDWR | O_NOCTTY);
grantpt(master);
unlockpt(master);
const char *slave = ptsname(master);

pid_t pid = fork();
if (pid == 0) {
    setsid();
    int fd = open(slave, O_RDWR);
    ioctl(fd, TIOCSCTTY, 0);
    dup2(fd, STDIN_FILENO);
    dup2(fd, STDOUT_FILENO);
    dup2(fd, STDERR_FILENO);
    close(master);
    close(fd);
    execvp(argv[0], argv);
    _exit(127);
}
/* 父进程：read/write master；窗口变化时 ioctl(master, TIOCSWINSZ, &ws) */

PRoot 启动参数（示例，路径按实际替换）

proot \
  --link2symlink \
  --kill-on-exit \
  --sysvipc \
  --shared-tmp \
  -0 \
  -r "$ROOTFS" \
  -b /dev -b /proc -b /sys \
  -b "$HOME/storage:/mnt/sdcard" \
  /usr/bin/env -i \
    HOME=/root \
    TERM=xterm-256color \
    LANG=C.UTF-8 \
    PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
  /bin/bash -l

--link2symlink 处理 Android 文件系统对硬链接的限制；-0 伪造 uid 0；--kill-on-exit 防止残留进程；--shared-tmp 与 --sysvipc 解决部分工具对 tmp 与 SysV IPC 的依赖。绑定共享存储会扩大数据暴露面，默认关闭，由用户显式开启。

root chroot（示例；需 su 与清理）

su -c '
  ROOT=/data/data/com.kingkang/files/rootfs/kali-arm64
  mount -t proc proc "$ROOT/proc"
  mount --bind /dev "$ROOT/dev"
  mount --bind /sys "$ROOT/sys"
  chroot "$ROOT" /usr/bin/env -i \
    HOME=/root TERM=xterm-256color LANG=C.UTF-8 \
    PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
    /bin/bash -l
'

生产实现应把挂载放进独立 mount namespace（设备支持时用 unshare -m），并用 trap/退出回调确保卸载。应用崩溃或被强杀时，下次启动先做一次挂载点健康检查。

rootfs 清单（manifest）

{
  "id": "kali-arm64",
  "version": "2026.2",
  "arch": "aarch64",
  "url": "https://mirror.example/kali-arm64-2026.2.tar.xz",
  "sha256": "…",
  "size": 1234567890,
  "min_free_bytes": 6442450944,
  "signature": "…",
  "key_id": "kingkang-rootfs-2026"
}

校验顺序固定为：manifest 签名 → 下载文件的 SHA-256 → 解压前检查剩余空间 → 解压后校验关键路径与文件模式。任何一步失败都不能启动运行时。manifest 与签名公钥随应用更新，不依赖单一 CDN。

05 / Kali

Kali 集成

Kali 不是特殊内核，而是 Debian 衍生发行版加一套工具。真正难的是权限与能力：同一套 rootfs，在无 root 的 PRoot 里和在有 root 的 chroot 里，能跑的工具不是一回事。

5.1 三种交付形态

形态前提能力适用
NetHunter Rootless无 root；Termux（官方文档基线）绝大多数 CLI 工具、apt、Metasploit、KeX 图形；无 raw socket / mount / 监听模式默认形态，覆盖学习与日常测试
Root chroot已 root；stock 内核接近原生；raw socket、iptables、mount；仍无监听模式与 HID进阶用户、需要完整网络工具
NetHunter Fullroot + NetHunter 内核 + recovery监听模式、数据包注入、USB HID、蓝牙 HID 等专业场景；刷机风险与设备矩阵限制

5.2 Rootless 引导流程

  1. 从 NetHunter 官方目录（kali.download/nethunter-images/current/rootfs）获取 full rootfs 与校验值：arm64 约 1.8 GB、amd64 约 2.2 GB。当前版本直接固定官方文件名并内置 SHA-256；更新时比对同目录 SHA256SUMS 中发布的校验值。
  2. 校验 rootfs 的 SHA-256；检查剩余空间（建议至少 10 GB，完整工具 15–20 GB）。安装记录已写入镜像的校验值，设置页的“检查更新”用它判断 Kali 是否发布了新镜像，有更新时自动下载替换，并保留 /root 与 /opt/kingkang。
  3. 用 libarchive 解压，保留符号链接与权限位；处理 Android 对硬链接的限制。解压后写入 /etc/resolv.conf、locale、时区与 apt 镜像。
  4. 首次启动执行 apt update 与 apt full-upgrade，再按用户选择安装 kali-linux-headless 或工具子集。提供“最小安装 / 完整工具”两个档位，避免默认下载十几 GB。
  5. 可选图形：启动 KeX/VNC，应用通过 intent 拉起 VNC 客户端；或在 P2 接入 Termux:X11。
  6. 提供 rootfs 备份与恢复（tar + 排除缓存），并在升级失败时回滚到上一版本。

5.2.1 DeepSeek Harness 与 Kali 的集成方式

dsh 不是 Android 侧的独立进程，而是 Kali rootfs 内的一套 Node.js 工具链。应用负责准备运行环境、安装与升级 dsh，并拉起同在该 rootfs 内的 bridge.mjs；桥接作为应用前台服务的子进程持有 dsh 的 web profile，向应用暴露 KK-Agent v1。rootfs 备份或删除时，dsh 与会话随之迁移或移除，不会留下系统级残留。

  • Node.js 与 dsh 固定安装在 /opt/kingkang，入口软链到 /usr/local/bin，不覆盖 Kali 自带工具。
  • 安装脚本写入 rootfs 的 /tmp，通过 PRoot 执行，避免在 UI 或 ViewModel 中拼接 shell。
  • 脚本以 KK_* 行输出状态与版本，错误码由应用翻译成可读提示；命令超时可取消，失败不伪造成功。
  • 只使用 nodejs.org 官方二进制与 DeepSeek 官方 npm 包；下载的 Node.js tarball 必须通过 SHASUMS256.txt 校验。
  • Node.js 由应用通过 HTTPS 下载、校验后用系统 tar 解压进 rootfs，不经过 guest 的 apt / curl；npm 使用 Node 自带的 CA 证书访问官方 registry。

5.5 存储与性能

  • 目录型 rootfs 放在应用私有存储，避免镜像挂载（无 root 也无法 mount）。备份用 tar，不使用 sparse image。
  • 默认最小安装约 4–6 GB 可用空间；完整 Kali 工具建议 15–20 GB。下载前做空间预检，解压时预留 2 倍峰值。
  • PRoot 下 apt 与编译偏慢，UI 要给出“正在解包/配置”的真实进度，避免用户误判卡死。
  • apt 缓存、旧内核与日志需要清理入口；提供“回收空间”而不是让用户手敲命令。
  • 设备发热与电量：长任务提示充电；会话空闲时释放 wake lock。
Kali 专项提醒

proot-distro 的官方发行版列表未收录 Kali；社区有 --override-url 与 fork 方案，但版本与维护不稳定。产品应以 NetHunter Rootless 的 rootfs 与启动流程为基线，并自行维护 manifest、镜像与回滚，而不是依赖某个社区脚本的当前行为。

6.1 首次启动流程

  2. 选择下载镜像与镜像源；显示实时速度、剩余时间与暂停/续传。
  3. 校验签名与哈希；失败时给出具体失败项与重试入口。
  4. 解压并展示可读的启动日志，而不是空白转圈；允许取消并清理半成品。
  5. 进入终端，显示一条可复制的示例命令（如 uname -a），确认环境可用。

07 / Security

安全、合规与发行

这个应用的设计前提是“执行任意 Linux 程序”。它不可能像普通笔记应用那样收紧权限，因此安全工作的重点不是阻止执行，而是明确边界、保护供应链、控制爆炸半径。

7.1 威胁模型

资产 / 边界威胁缓解
rootfs 供应链镜像被篡改、镜像源被劫持、过期工具链manifest 签名 + SHA-256 + 多源；构建可复现；发布 SBOM
应用私有数据容器内恶意程序读取 token、会话、配置明确“PRoot 不是沙箱”；敏感信息放 Keystore；默认不绑定外部存储
共享存储误删用户文件、泄露文档默认不绑定；按需授权；只读挂载优先；删除需确认
组件边界外部应用拉起会话、读取日志、注入命令组件不导出；PendingIntent immutable；FileProvider 最小路径；校验调用方
root 模式提权后被恶意脚本滥用显式开启 + 二次确认；生物识别锁；卸载清理；审计日志
法律与政策被用于未授权测试；商店下架授权使用声明；不内置载荷；主渠道自建；保留合规文档

7.2 应用加固清单

  • allowBackup="false"；会话 token 与 SSH 私钥使用 Android Keystore 包装，不写入明文配置。
  • 所有组件默认 exported="false"；必须导出的入口加签名级权限或调用方校验。
  • 网络使用 Network Security Config，禁止明文；下载与 manifest 使用固定公钥校验，不只依赖 TLS。
  • release 关闭 debuggable，开启 R8；NDK 开启 PIE、RELRO、stack protector、_FORTIFY_SOURCE。
  • 日志不记录命令内容与输出；诊断包由用户主动导出，导出前预览。
  • 截图保护可选；切换后台时对终端内容做模糊，避免任务切换泄露。
  • root 模式启动前显示能力与风险说明；退出时强制卸载并检查残留。

7.3 发行渠道与 targetSdk 策略

W^X 只有三种现实选择：

  • B. 现代 targetSdk + APK 原生库 / linker64：Termux 的 Play 版本已经证明可行，但依赖启动路径与环境变量，任何静态链接或清空环境的程序都可能失效；维护成本高，且仍可能触碰 Play 政策。

16 KB 页大小必须作为独立门禁：NDK r28+ 构建、-Wl,-z,max-page-size=16384、用官方校验脚本检查所有 .so；Kali rootfs 中的关键二进制也要在 16 KB 设备/模拟器上验证。不要等到 Play 或系统强制时才处理。

7.4 合规要点

  • 授权使用：首次启动与每次进入 Kali 工具集时提示仅限授权测试；不提供“一键攻击”模板。
  • 不自动提权：不集成一键 root、不下载未知来源的内核或 recovery。
  • 出口管制与当地法律：部分加密与渗透工具受出口管制；按目标市场评估。
  • 许可证：GPLv3 源码义务、Apache NOTICE、PRoot GPLv2、Kali 工具混合许可证，逐项审计。
  • 商标与品牌：不使用 Kali/Termux/NetHunter 的官方 logo，不暗示官方合作。
  • 隐私：默认不上传命令、文件名、网络目标；崩溃上报需明示并可选关闭。

8.2 技术栈

  • Kotlin + Jetpack Compose；终端表面用 Canvas/SurfaceView，避免 Compose 文本布局扛不住大吞吐。
  • NDK r28+、C++20、CMake；arm64-v8a 为主，x86_64 仅用于模拟器调试。
  • 下载用 OkHttp（Range 续传），解压用 libarchive + liblzma；签名用 Ed25519（Tink/BouncyCastle 或 libsodium）。
  • 元数据用 DataStore/Room；大文件任务用前台服务，不用 WorkManager 承担解压。
  • 依赖注入从简：Hilt 可选；核心模块保持纯 Kotlin，便于单元测试。

总计 16–20 周，按 2 名工程师（1 Android、1 native/运行时）+ 0.5 名设计/QA 估算。单人开发通常需要 5–6 个月。M0 失败的唯一合理结论是换执行路径，而不是继续堆 UI。

风险概率影响缓解
